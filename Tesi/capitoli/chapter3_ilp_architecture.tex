\chapter{System Architecture, Mathematical Formulation, and Implementation}
\label{chap:ilp_architecture}

This chapter provides a comprehensive dissertation on the theoretical framework, mathematical optimization formulation, and concrete software architecture of the proposed Centralized Integer Linear Programming (ILP) Orchestrator. 
In satellite edge computing, theoretical formulations often suffer from an abstraction penalty: static graph models fail to capture the physical reality of rapid orbital kinematics, fluctuating inter-satellite links, and discrete queue dynamics. 
To bridge this gap, each section systematically couples the formal analytical modeling with its concrete algorithmic realization. The full simulation environment is developed in Python using the \texttt{SimPy} discrete-event engine~\cite{simpy2023} and the \texttt{PuLP} mathematical programming library~\cite{pulp2011} backed by the open-source \texttt{HiGHS} branch-and-cut solver~\cite{huangfu2018highs}. The complete, documented source code is publicly accessible in the reference repository~\cite{bagini_repo_2026}.

The remainder of this chapter is structured as follows. Section~\ref{sec:system_model} formalizes the regional Walker-Delta constellation, the offloading task abstraction, and the decoupled three-phase operational circuit. 
Section~\ref{sec:dynamic_batching} details the event-driven batching engine designed to throttle solver invocation while enforcing bounded delay. 
Section~\ref{sec:constellation_mapping} introduces the multi-source topology exploration and dimension-free metric normalization scheme. 
Section~\ref{sec:mathematical_model} derives the multi-objective ILP formulation, its physical constraints, and the cascade diagnostic engine for dropped tasks. 
Section~\ref{sec:task_execution_routing} elaborates on task dispatching, buffer re-enqueuing, and the hybrid routing protocol combining planned ILP paths with reactive greedy geometric recovery. 
Finally, Section~\ref{sec:complexity_analysis} provides an asymptotic complexity and scalability analysis covering runtime footprint and control telemetry overhead.

\section{Regional Constellation Architecture and Offloading Model}
\label{sec:system_model}

We model a regional Low Earth Orbit (LEO) satellite network operating within a Walker-Delta orbital constellation~\cite{walker1984satellite, survey_orbital_edge_2023}. 
LEO satellites traverse circular orbits at altitudes ranging between $500\text{ km}$ and $1200\text{ km}$, resulting in orbital velocities exceeding $7.5\text{ km/s}$ and orbital periods of roughly $90\text{--}100\text{ minutes}$. 
The operational network comprises a set of candidate Satellite Edge Nodes (SENs), denoted by $S = \{1, 2, \dots, n\}$, and a set of regional Access Points (APs) or satellite ground stations, denoted by $AP_{global}$~\cite{icdcs_satellite_2025}. 
Each SEN is equipped with compute capabilities, a finite battery reserve, and inter-satellite communication transceivers. 
Within the observed geographical region, a designated coordinator acts as the centralized \emph{Master Orchestrator}. The Master maintains real-time visibility over constellation kinematics, dynamic processor queue occupancies, residual energy budgets, and active Inter-Satellite Link (ISL) topologies. 
The orchestration logic and event management are implemented in the \texttt{Orchestrator} class, while the physical state of orbital nodes is encapsulated in \texttt{EdgeServer.py}~\cite{bagini_repo_2026}.

Ground Users (GUs) deploy compute-intensive applications (e.g., Earth observation inference, disaster response imagery processing) whose requests arrive dynamically at regional gateways. 
Each offloading request $r \in R$ is represented by a five-element tuple:
\begin{equation}
    r = \left( d_{cpu,r}, D_r, s_r, t_{arr}, AP_r \right)
\end{equation}
where $d_{cpu,r}$ is the computational workload execution demand (in seconds), $D_r$ represents the maximum allowable service processing deadline, $s_r$ denotes the input dataset payload size (in MB), $t_{arr}$ is the arrival timestamp at the entry node, and $AP_r \in AP_{global}$ denotes the originating ground access point~\cite{icdcs_satellite_2025}.

\subsection{The Decoupled Three-Phase Lifecycle}
\label{subsec:decoupled_lifecycle}

Due to the extreme relative velocity between the LEO space segment and ground reference points, the topology of the network is inherently time-varying. 
A satellite visible to a ground station at arrival timestamp $t_{arr}$ may traverse its elevation cone and disappear behind the local horizon within $5\text{--}10\text{ minutes}$. 
To prevent solver stale-state failure and guarantee deterministic execution, the lifecycle of each offloaded task $r$ is decoupled into three distinct operational phases:
\begin{enumerate}
    \item \textbf{Uplink Multi-Hop Forwarding Phase ($T_{up}$):} The originating gateway $AP_r$ injects the task input payload $s_r$ into the orbital network. The payload is forwarded across a multi-hop ISL path $\vec{P}_{up}(AP_r, i)$, traversing $h_{up}(r,i)$ intermediate satellite hops until it reaches the selected compute node $i \in S$~\cite{icdcs_satellite_2025}.
    \item \textbf{On-Board Computational Execution Phase ($T_{cpu}$):} Upon arrival at satellite $i$, the task is enqueued into the local processor schedule. The overall execution delay encompasses both the queuing wait time $W_{cpu,i}$ and the physical compute duration $d_{cpu,r}$~\cite{denby2019orbital, icdcs_satellite_2025}.
    \item \textbf{Post-Execution Geographic Result Delivery ($T_{down}$):} Once computation terminates, the resulting output payload must be transferred back to the originating ground gateway $AP_r$. 
\end{enumerate}

\paragraph{Design Rationale for Algorithmic Decoupling.} 
In traditional terrestrial edge computing, dispatchers optimize both forward and return paths simultaneously. In LEO networks, however, the latency required to execute long-running tasks ($W_{cpu,i} + d_{cpu,r} \gg 10\text{ s}$) frequently exceeds the stability window of individual laser ISL alignments. 
Jointly planning the downlink path at time $t_{arr}$ would force the optimizer to rely on long-range topological predictions that are vulnerable to transient link disruptions, orbital plane crossings, and ground station visibility loss. 
Consequently, the centralized ILP orchestrator restricts its search space to the joint optimization of satellite candidate selection, uplink ISL forwarding, energy conservation, and deadline compliance. 
The return phase ($T_{down}$) is delegated to a distributed, autonomous geographic greedy routing protocol executed on-demand at execution completion time.

\section{Event-Driven Dynamic Batching Engine}
\label{sec:dynamic_batching}

Formulating and solving an NP-hard Mixed-Integer Linear Program for every incoming task arrival introduces prohibitive computational latency. 
Under high offloading request rates $\lambda$, instantaneous per-task optimization causes compute-orchestrator starvation: the time spent by the Master node searching the branch-and-bound tree exceeds the task inter-arrival time, resulting in an unstable queuing regime~\cite{wolsey1998integer, icdcs_satellite_2025}. 
Conversely, static time-window batching introduces artificial buffering delay, potentially causing deadline violations for latency-sensitive tasks during light traffic periods.

To reconcile these competing operational demands, the Master Orchestrator implements an event-driven dynamic batching mechanism within a \texttt{SimPy} discrete-event environment~\cite{simpy2023}. 
The engine is parameterized by two complementary thresholds:
\begin{itemize}
    \item \textbf{Maximum Batch Size ($BS$):} A capacity ceiling that limits the cardinality of the task set $|R|$ submitted to the solver. Bounding $|R|$ bounds the binary variable space $|R| \times |S|$, establishing a deterministic upper limit on branch-and-cut execution time.
    \item \textbf{Batch Timeout ($BT$):} A temporal window that bounds the maximum buffering delay experienced by any single request, preventing starvation during low-throughput operational phases.
\end{itemize}

\subsection{State Consistency and Discrete-Event Synchronization}
\label{subsec:event_synchronization}

In a discrete-event simulation model, physical processes (e.g., satellite movement, inter-satellite distance variations, queue servicing) evolve concurrently across distinct simulation threads. 
Satellite coordinates and elevation angles are updated dynamically according to orbital ephemeris~\cite{vallado2006sgp4}. 
If the orchestrator were to capture constellation telemetry immediately upon the satisfaction of a batch trigger, pending thread events scheduled at the exact simulation time $t$ might remain uncommitted, leading to stale queue readings or inconsistent link states.

To enforce strict state consistency, the orchestrator introduces a zero-delay event barrier:
\begin{equation}
    \mathbf{yield} \quad \Call{Timeout}{env, 0}
\end{equation}
This operational step temporarily relinquishes thread execution back to the \texttt{SimPy} event scheduler. 
The engine flushes and commits all physical updates occurring at time $t$ across the entire constellation before the orchestrator initiates graph extraction and solver instantiation.

Algorithm~\ref{alg:dynamic_batching} formalizes the dual lifecycle of task ingestion and batch dispatching, corresponding to the \texttt{add\_task}, \texttt{\_run\_loop}, and \texttt{\_process\_batch} methods of \texttt{Orchestrator.py}~\cite{bagini_repo_2026}.

\begin{algorithm}[H]
\caption{Event-Driven Batch Ingestion and Orchestrator Lifecycle}
\label{alg:dynamic_batching}
\small
\begin{algorithmic}[1]
\Require Simulation environment $env$, buffer capacity $BS$, timeout duration $BT$
\Ensure Aggregation of incoming tasks into batches and invocation of optimization pipeline
\State \textbf{Global State:} $\mathcal{B} \gets [\,]$, $E_{arrival} \gets \Call{CreateEvent}{env}$, $E_{ready} \gets \Call{CreateEvent}{env}$
\Statex
\Procedure{AddTask}{$task\_data, task\_id, visible\_aps$} \Comment{Invoked upon task arrival}
    \If{$\mathcal{B} = [\,]$ \textbf{and} $\neg \Call{IsTriggered}{E_{arrival}}$}
        \State $\Call{TriggerEvent}{E_{arrival}}$ \Comment{Signal arrival of first batch task}
    \EndIf
    \State Append $(task\_id, task\_data, visible\_aps, env.now)$ to $\mathcal{B}$
    \If{$|\mathcal{B}| \ge BS$ \textbf{and} $\neg \Call{IsTriggered}{E_{ready}}$}
        \State $\Call{TriggerEvent}{E_{ready}}$ \Comment{Signal maximum capacity reached}
    \EndIf
\EndProcedure
\Statex
\Procedure{RunLifecycleLoop}{} \Comment{Continuous orchestrator background thread}
    \Loop
        \If{$\mathcal{B} = [\,]$}
            \State \textbf{await} $E_{arrival}$ \Comment{Sleep until first request arrives}
        \EndIf
        \State $E_{timeout} \gets \Call{StartTimer}{env, BT}$ \Comment{Start temporal aggregation window}
        \State \textbf{await} $E_{ready} \lor E_{timeout}$ \Comment{Wake on capacity reached or timeout expiration}
        \If{$\mathcal{B} \neq [\,]$}
            \State \textbf{yield} $\Call{Timeout}{env, 0}$ \Comment{Commit concurrent physical and orbital updates}
            \State $\Call{ProcessBatch}{}$
        \EndIf
        \State $E_{arrival} \gets \Call{CreateEvent}{env}$, \quad $E_{ready} \gets \Call{CreateEvent}{env}$ \Comment{Reset triggers}
    \EndLoop
\EndProcedure
\Statex
\Procedure{ProcessBatch}{} \Comment{Batch execution pipeline}
    \State $\mathcal{B}_{active} \gets \mathcal{B}, \quad \mathcal{B} \gets [\,]$
    \State $(\mathcal{T}_{route}, \mathcal{M}_{nodes}) \gets \Call{MapConstellationTopology}{}$
    \State $\mathcal{A} \gets \Call{SolveILP}{\mathcal{T}_{route}, \mathcal{M}_{nodes}, \mathcal{B}_{active}}$
    \State $\Call{DispatchTasks}{\mathcal{A}}$
\EndProcedure
\end{algorithmic}
\end{algorithm}

\section{Constellation Topology Mapping and Metric Normalization}
\label{sec:constellation_mapping}

Before formulating the optimization model, the Master Orchestrator must compute the optimal multi-hop ISL routing paths from every active ground Access Point to all candidate Satellite Edge Nodes. 
This exploration is conducted by the \texttt{\_map\_constellation} method in \texttt{Orchestrator.py} using a Multi-Source Dijkstra shortest-path algorithm~\cite{dijkstra1959note, bagini_repo_2026}.

\subsection{Dimensionless Link Cost Normalization}
\label{subsec:metric_normalization}

A major challenge in evaluating dynamic satellite links lies in the dimensional disparity between physical performance metrics. 
Directly summing link propagation latency (measured in milliseconds) and radio frequency/optical transmission energy (measured in microjoules or joules) is physically inconsistent and introduces scale bias into shortest-path calculations. 
Furthermore, the actual payload size $s_r$ varies across requests, making it impossible to compute a single static link weight that accurately reflects every pending task.

To decouple graph exploration from individual task sizes, each directed inter-satellite edge $(u, v)$ is probed using a standardized reference payload:
\begin{equation}
    S_{ref} = 1~\text{MB} = 1024^2~\text{bytes}
\end{equation}
For an edge $(u, v)$ characterized by propagation delay $\tau_{u,v}$ ($\tau_{u,v} = \frac{C}{D_{u,v}}$ where $C$ is the speed of light and $D_{u,v}$ is the distance between nodes) and transmission bandwidth $B_{u,v}$ (in Bytes/s), the physical traversal time and energy consumption for the reference payload over optical ISL channels~\cite{chen2021isl, chaudhry2021laser} are formulated as:
\begin{equation}
    t_{link}(u,v) = \tau_{u,v} + \frac{S_{ref}}{B_{u,v}}
    \label{eq:t_link}
\end{equation}
\begin{equation}
    e_{link}(u,v) = P_{net} \cdot \frac{S_{ref}}{B_{u,v}}
    \label{eq:e_link}
\end{equation}
where $P_{net}$ is the active laser transceiver power (\texttt{Ptrasm})~\cite{icdcs_satellite_2025}.

To compute a composite, scale-free cost, the metrics are normalized against theoretical upper bounds, $T_{max}$ and $E_{max}$. 
These bounds represent a worst-case link operating under minimum network bandwidth ($B_{min} = 100~\text{KB/s}$) and maximum slant propagation delay ($\tau_{max} = 100~\text{ms}$):
\begin{equation}
    T_{max} = \tau_{max} + \frac{S_{ref}}{B_{min}}, \quad E_{max} = P_{net} \cdot \frac{S_{ref}}{B_{min}}
\end{equation}
The dimensionless, normalized delay and energy metrics are thus:
\begin{equation}
    \hat{t}_{link}(u,v) = \frac{t_{link}(u,v)}{T_{max}}, \quad \hat{e}_{link}(u,v) = \frac{e_{link}(u,v)}{E_{max}}
\end{equation}
The composite scalar cost $c_{link}(u,v) \in [0, 1]$ is established as a convex combination governed by the user-defined routing policy weights $w_R$ (\texttt{centralized\_w\_r}) and $w_e$ (\texttt{centralized\_w\_e}):
\begin{equation}
    c_{link}(u,v) = w_R \cdot \hat{t}_{link}(u,v) + w_e \cdot \hat{e}_{link}(u,v), \quad \text{where } w_R + w_e = 1
\end{equation}

\paragraph{Structural Decoupling Principle.} 
The Multi-Source Dijkstra procedure uses $S_{ref}$ solely to discover the structural shortest-path backbone $\vec{P}_{up}(AP_r, i)$ between access points and candidate satellites. 
Once these paths are established, the subsequent ILP optimization model scales transmission delay and forwarding energy according to the actual input payload size $s_r^{bytes} = s_r \cdot 1024^2$ of each individual request. 

Concurrently with path discovery, the orchestrator queries all candidate nodes in \texttt{globals.edge\_servers} to construct an up-to-date telemetry state snapshot:
\begin{equation}
    \mathbf{v}_i = \left[ B_i, W_{cpu,i}, W_{net,i}, C_{sen,i}, \kappa_i, t_{sunset,i} \right]
\end{equation}
capturing residual battery levels, CPU queue wait times, network queue buffer latencies, processor frequencies, switching capacitance coefficients, and orbital eclipse horizons. 
The complete procedure is formalized in Algorithm~\ref{alg:constellation_mapping}.

\begin{algorithm}[H]
\caption{Multi-Source Constellation Topology and Telemetry Mapping}
\label{alg:constellation_mapping}
\small
\begin{algorithmic}[1]
\Require Access points $AP_{global}$, satellites $S$, weights $w_R, w_e$, reference size $S_{ref}$, bounds $T_{max}, E_{max}$
\Ensure Routing table $\mathcal{T}_{route}$ and node operational telemetry dictionary $\mathcal{M}_{nodes}$
\State $\mathcal{T}_{route} \gets \emptyset, \quad \mathcal{M}_{nodes} \gets \emptyset$
\ForAll{$ap \in AP_{global}$}
    \State $\mathcal{T}_{route}[ap] \gets \emptyset$
    \State Initialize min-heap $\mathcal{Q} \gets \emptyset$, distance map $dist[v] \gets \infty, \forall v \in (AP_{global} \cup S)$
    \State $dist[ap] \gets 0.0$
    \State $\Call{Push}{\mathcal{Q}, (0.0, 0.0, 0.0, ap, [ap])}$ \Comment{Store $(cost, time, energy, access point, path)$}
    \While{$\mathcal{Q} \neq \emptyset$}
        \State $(cost, time, energy, u, path) \gets \Call{PopMin}{\mathcal{Q}}$
        \If{$cost > dist[u]$}
            \State \textbf{continue}
        \EndIf
        \If{$u \in S$}
            \State $\mathcal{T}_{route}[ap][u] \gets \{ \text{cost}: cost, \text{time}: time, \text{energy}: energy, \text{path}: path \}$
        \EndIf
        \ForAll{$v \in \Call{Neighbors}{u}$}
            \State $\tau_{u,v} \gets \Call{GetLatency}{u, v}, \quad B_{u,v} \gets \Call{GetBandwidth}{u, v} \cdot 1024^2$
            \If{$B_{u,v} \le 0$} \Comment{Skip inactive or broken links}
                \State \textbf{continue}
            \EndIf
            \State $t_{hop} \gets \tau_{u,v} + \frac{S_{ref}}{B_{u,v}}, \quad e_{hop} \gets P_{net} \cdot \frac{S_{ref}}{B_{u,v}}$
            \State $\hat{t} \gets t_{hop} / T_{max}, \quad \hat{e} \gets e_{hop} / E_{max}$
            \State $c_{link} \gets w_R \cdot \hat{t} + w_e \cdot \hat{e}$
            \If{$dist[u] + c_{link} < dist[v]$}
                \State $dist[v] \gets dist[u] + c_{link}$
                \State $\Call{Push}{\mathcal{Q}, (dist[v], time + t_{hop}, energy + e_{hop}, v, path \cup [v])}$
            \EndIf
        \EndFor
    \EndWhile
\EndFor
\ForAll{$i \in S$} \Comment{Capture telemetry snapshot across all candidate compute nodes}
    \State $W_{cpu,i} \gets \Call{W\_cpu}{i}, \quad W_{net,i} \gets \Call{W\_net}{i}$
    \State $B_i \gets \Call{GetEnergy}{i}, \quad C_{sen,i} \gets \Call{GetClockSpeed}{i}, \quad t_{sunset,i} \gets \Call{GetSunset}{i}$
    \State $\mathcal{M}_{nodes}[i] \gets \{ B_i, W_{cpu,i}, W_{net,i}, C_{sen,i}, \kappa_i, t_{sunset,i} \}$
\EndFor
\State \Return $(\mathcal{T}_{route}, \mathcal{M}_{nodes})$
\end{algorithmic}
\end{algorithm}

\section{Centralized Integer Linear Programming Formulation}
\label{sec:mathematical_model}

Let $R$ be the set of tasks accumulated within the current batch ($|R| \le BS$) and $S$ the set of candidate Satellite Edge Nodes. 
Building upon combinatorial optimization theory~\cite{wolsey1998integer, boyd2004convex}, the decision space is modeled via two sets of binary decision variables:
\begin{align}
    x_{r,i} &\in \{0, 1\}, \quad \forall r \in R, \, \forall i \in S \quad \text{(1 if task $r$ is assigned to SEN $i$; 0 otherwise)} \\
    y_r &\in \{0, 1\}, \quad \forall r \in R \quad \text{(1 if task $r$ is explicitly rejected; 0 otherwise)}
\end{align}

\subsection{Physical Delay, Energy, and Orbital Eclipse Modeling}
\label{subsec:latency_energy_models}

For each candidate assignment pair $(r, i)$, the total predicted response time $R_{r,i}$ accounts for the multi-hop transmission delay of the actual payload $s_r^{bytes} = s_r \cdot 1024^2$ along path $\vec{P}_{up}(AP_r, i)$, network buffering delays at intermediate hops, and compute queue and execution times at satellite $i$~\cite{icdcs_satellite_2025}:
\begin{equation}
    R_{r,i} = \underbrace{\sum_{(u,v) \in \vec{P}_{up}(AP_r, i)} \left( W_{net,u} + \frac{s_r^{bytes}}{B_{u,v}} + \tau_{u,v} \right)}_{T_{up}(r,i)} + \left( W_{cpu,i} + d_{cpu,r} \right)
    \label{eq:total_latency}
\end{equation}

Similarly, the cumulative fleet energy expenditure $\epsilon_{r,i}$ evaluates the communication energy expended by all intermediate forwarding satellites along $\vec{P}_{up}(AP_r, i)$, combined with the dynamic CPU energy consumed by destination node $i$ during local processing:
\begin{equation}
    \epsilon_{r,i} = \sum_{(u,v) \in \vec{P}_{up}(AP_r, i)} P_{net} \frac{s_r^{bytes}}{B_{u,v}} + \kappa_i \cdot d_{cpu,r} \cdot C_{sen,i}^3
    \label{eq:total_energy}
\end{equation}
The CPU energy model is derived from dynamic CMOS switching power dissipation:
\begin{equation}
    P_{cpu} = \kappa_i \cdot C_{sen,i}^3
\end{equation}
which, integrated over the computational duration $d_{cpu,r}$, yields the second term in Equation~\eqref{eq:total_energy}~\cite{icdcs_satellite_2025}.

To protect satellites approaching orbital eclipse from battery depletion, we define an orbital sunset penalty $\Omega_i \in [0, 1]$. 
Assigning tasks to a node nearing eclipse risks unexpected outages. 
Let $t_{sunset,i}$ represent the remaining visibility time for satellite $i$. The penalty factor is defined as:
\begin{equation}
    \Omega_i = \begin{cases}
        1.0 - \frac{t_{sunset,i}}{\max_{k \in S} (t_{sunset,k})}, & \text{if } \max_{k \in S} (t_{sunset,k}) > 0 \\
        1.0, & \text{if } t_{sunset,i} = 0 \\
        0.0, & \text{otherwise}
    \end{cases}
\end{equation}
This term penalizes allocations to satellites entering eclipse without introducing non-linear step-function discontinuities into the objective function.

\subsection{Multi-Objective Function and System Constraints}
\label{subsec:objective_constraints}

Task rejection ($y_r = 1$) is penalized via a large scalar coefficient $P_{drop} = 10^6$. 
This ensures that the solver rejects tasks only when physical capacity, energy, or deadline constraints make acceptance strictly infeasible. 
The global fleet performance metrics for delay ($Z_{time}$), energy ($Z_{energy}$), and eclipse degradation ($Z_{sunset}$) are defined as:
\begin{align}
    Z_{time} &= \sum_{r \in R} \sum_{i \in S} x_{r,i} R_{r,i} + \sum_{r \in R} y_r P_{drop} \\
    Z_{energy} &= \sum_{r \in R} \sum_{i \in S} x_{r,i} \epsilon_{r,i} + \sum_{r \in R} y_r P_{drop} \\
    Z_{sunset} &= \sum_{r \in R} \sum_{i \in S} x_{r,i} \Omega_i
\end{align}

Depending on the operational strategy configured via \texttt{centralized\_primary\_objective} (Time-first vs. Energy-first), the composite objective function $Z$ applies hierarchical scalar weights ($\alpha, \beta, \gamma$)~\cite{boyd2004convex, zhong2025leo}:
\begin{equation}
    \min Z = \begin{cases}
        \alpha Z_{time} + \beta Z_{energy} + \gamma Z_{sunset}, & \text{if primary strategy is Time} \\
        \alpha Z_{energy} + \beta Z_{time} + \gamma Z_{sunset}, & \text{if primary strategy is Energy}
    \end{cases}
    \label{eq:objective_function}
\end{equation}
where $\alpha$ scales the primary objective, $\beta$ weights the secondary objective, and $\gamma$ governs the eclipse penalty.

The feasible assignment space is governed by four linear constraints:
\begin{enumerate}
    \item \textbf{Decision Uniqueness:} Every offloaded request $r \in R$ must either be allocated to exactly one satellite node $i \in S$ or explicitly dropped:
    \begin{equation}
        \sum_{i \in S} x_{r,i} + y_r = 1, \quad \forall r \in R
        \label{eq:constraint_uniqueness}
    \end{equation}
    \item \textbf{Strict Processing Deadline Compliance:} The cumulative predicted latency (uplink forwarding, queue buffering, and execution) must not exceed the application deadline $D_r$~\cite{icdcs_satellite_2025}:
    \begin{equation}
        x_{r,i} \cdot R_{r,i} \le D_r, \quad \forall r \in R, \, \forall i \in S
        \label{eq:constraint_deadline}
    \end{equation}
    If candidate satellite $i$ cannot satisfy the deadline ($R_{r,i} > D_r$), the linear constraint forces $x_{r,i} = 0$.
    \item \textbf{Distributed Fleet Energy Budget:} The total energy required from satellite $k \in S$—both as an intermediate packet forwarder along path $\vec{P}_{up}(AP_r, i)$ and as a compute node—must not exceed its usable residual battery budget $B_k$:
    \begin{equation}
        \sum_{r \in R} \sum_{i \in S} x_{r,i} \cdot \epsilon_{r,i,k} \le B_k, \quad \forall k \in S
        \label{eq:constraint_energy}
    \end{equation}
    where $\epsilon_{r,i,k}$ captures the specific energy portion expended by satellite $k$ when task $r$ is processed on satellite $i$.
    \item \textbf{Constellation Load Balancing (Anti-Congestion):} To prevent localized bottlenecks and head-of-line blocking in satellite compute queues, the solver caps the total number of tasks allocated to any single satellite within the batch:
    \begin{equation}
        \sum_{r \in R} x_{r,i} \le \left\lfloor \frac{|R|}{|S|} \right\rfloor + 5, \quad \forall i \in S
        \label{eq:constraint_load_balancing}
    \end{equation}
    The uniform distribution term $\lfloor |R| / |S| \rfloor$ establishes a fair-share baseline, while the constant slack term $+5$ allows the solver to opportunistically exploit high-performance or low-latency nodes when capacity permits~\cite{tang2003loadbalancing}.
\end{enumerate}

\subsection{Solver Resolution and Cascade Rejection Diagnostics}
\label{subsec:cascade_diagnostics}

The mathematical program is built dynamically in Python via \texttt{PuLP}~\cite{pulp2011} within the \texttt{\_solve\_ilp} method and solved using \texttt{HiGHS}~\cite{huangfu2018highs, bagini_repo_2026}. 
While conventional optimization formulations treat task rejection as an undifferentiated binary outcome ($y_r = 1$), root-cause attribution is essential for system monitoring and telemetry.

To provide operational visibility, when $y_r^* = 1$, the orchestrator executes a post-solution cascade diagnostic evaluation across all reachable candidate satellites $S_{reach}(r) \subseteq S$. 
For each candidate $i \in S_{reach}(r)$, the system evaluates physical feasibility conditions in order of operational priority:
\begin{enumerate}
    \item \textbf{No Route Found:} If the access point cannot establish a path to any candidate node ($S_{reach}(r) = \emptyset$), the drop cause is classified as \texttt{"No\_Route"}.
    \item \textbf{Deadline Violation:} If the path and execution delay exceed the deadline ($R_{r,i} > D_r$), candidate $i$ is flagged as \texttt{"Deadline\_Violation"}.
    \item \textbf{Eclipse/Sunset Infeasibility:} If the projected execution window extends past the satellite's solar horizon ($R_{r,i} > t_{sunset,i}$), the candidate is classified as \texttt{"Sunset\_Violation"}.
    \item \textbf{Battery Energy Depletion:} If the node's residual battery is insufficient to cover compute or forwarding demands ($B_k - E_{allocated,k} < \epsilon_{r,i,k}$), candidate $i$ is labeled as \texttt{"Energy\_Exhaustion"}.
    \item \textbf{Capacity Saturation:} If node $i$ has already reached its allocation cap under the load balancing bound, it is marked as \texttt{"Load\_Balancing\_Rejected"}.
    \item \textbf{Global ILP Objective Trade-Off:} If candidate $i$ is physically capable of servicing the task, but the solver dropped it to avoid exceeding fleet-wide budget constraints or penalizing the global objective function, the assignment is recorded as \texttt{"Global\_ILP\_Conflict"}.
\end{enumerate}

Algorithm~\ref{alg:ilp_formulation} details the complete optimization assembly, branch-and-cut resolution, and the post-solution cascade diagnostics implemented in \texttt{\_solve\_ilp}~\cite{bagini_repo_2026}.

\begin{algorithm}[htbp]
\caption{ILP Problem Assembly, Resolution, and Cascade Diagnostics}
\label{alg:ilp_formulation}
\small
\begin{algorithmic}[1]
\Require Routing table $\mathcal{T}_{route}$, node states $\mathcal{M}_{nodes}$, batch $R$, weights $\alpha, \beta, \gamma$
\Ensure Task assignments list $\mathcal{A}$ with assigned nodes, paths, and rejection causes
\State $\mathcal{P} \gets \Call{CreateProblem}{\text{"Centralized\_ILP"}, \min}$
\State Instantiate variables: $x_{r,i} \in \{0, 1\}, \forall r \in R, i \in S$ and $y_r \in \{0, 1\}, \forall r \in R$
\Statex \Comment{\textbf{Step 1: Constraint Matrix Construction}}
\ForAll{$r \in R$}
    \State Add uniqueness constraint: $\sum_{i \in S} x_{r,i} + y_r = 1$ \Comment{Eq.~\eqref{eq:constraint_uniqueness}}
    \ForAll{$i \in S$}
        \State Compute predicted delay $R_{r,i}$ (Eq.~\eqref{eq:total_latency}) and energy $\epsilon_{r,i}$ (Eq.~\eqref{eq:total_energy})
        \State Add deadline constraint: $x_{r,i} \cdot R_{r,i} \le D_r$ \Comment{Eq.~\eqref{eq:constraint_deadline}}
    \EndFor
\EndFor
\ForAll{$k \in S$}
    \State Add battery constraint: $\sum_{r \in R} \sum_{i \in S} x_{r,i} \cdot \epsilon_{r,i,k} \le B_k$ \Comment{Eq.~\eqref{eq:constraint_energy}}
    \State Add load balance constraint: $\sum_{r \in R} x_{r,i} \le \lfloor |R| / |S| \rfloor + 5$ \Comment{Eq.~\eqref{eq:constraint_load_balancing}}
\EndFor
\Statex \Comment{\textbf{Step 2: Model Resolution}}
\State Set objective $Z$ (Eq.~\eqref{eq:objective_function}) and solve: $status \gets \Call{SolveHiGHS}{\mathcal{P}}$
\State $\mathcal{A} \gets [\,]$
\If{$status \notin \{\text{Optimal}, \text{Suboptimal}\}$}
    \State \Return $\mathcal{A}$ with all tasks $r \in R$ flagged as $\text{"Infeasible"}$
\EndIf
\Statex \Comment{\textbf{Step 3: Decision Extraction and Cascade Diagnostics}}
\ForAll{$r \in R$}
    \If{$y_r^* < 0.5$} \Comment{Task accepted}
        \State $i^* \gets \arg\max_{i \in S} x_{r,i}^*, \quad path \gets \mathcal{T}_{route}[AP_r][i^*]$
        \State Append $(r, i^*, path, \text{"Assigned"})$ to $\mathcal{A}$
    \Else \Comment{Task rejected: execute cascade diagnostic}
        \State $S_{reach} \gets \{i \in S \mid \mathcal{T}_{route}[AP_r][i] \text{ exists}\}$
        \State $cause \gets \text{"No\_Route"}$
        \If{$S_{reach} \neq \emptyset$}
            \State $\mathcal{C} \gets [\,]$
            \ForAll{$i \in S_{reach}$}
                \If{$R_{r,i} > D_r$}
                    \State Append $\text{"Deadline\_Violation"}$ to $\mathcal{C}$
                \ElsIf{$R_{r,i} > t_{sunset,i}$}
                    \State Append $\text{"Sunset\_Violation"}$ to $\mathcal{C}$
                \ElsIf{$B_i - E_{allocated,i} < \epsilon_{r,i}$}
                    \State Append $\text{"Energy\_Exhaustion"}$ to $\mathcal{C}$
                \ElsIf{$AllocatedCount(i) \ge MaxCap(i)$}
                    \State Append $\text{"Load\_Balancing"}$ to $\mathcal{C}$
                \Else
                    \State Append $\text{"Global\_ILP\_Conflict"}$ to $\mathcal{C}$
                \EndIf
            \EndFor
            \State $cause \gets \Call{DominantMode}{\mathcal{C}}$
        \EndIf
        \State Append $(r, \mathbf{null}, [\,], \text{"Scartato\_"} + cause)$ to $\mathcal{A}$
    \EndIf
\EndFor
\State \Return $\mathcal{A}$
\end{algorithmic}
\end{algorithm}

\section{Task Execution and Resilient Hybrid Routing}
\label{sec:task_execution_routing}

Once the solver generates the optimal assignment matrix $\mathcal{X}^*$, the orchestrator invokes \texttt{\_dispatch\_tasks} to process each decision. 
Depending on solver status and network availability, tasks are either routed, re-enqueued, or permanently dropped.

\subsection{Dispatching and Buffer Re-Enqueuing Pipeline}
\label{subsec:dispatching_pipeline}

The dispatching layer acts as an admission and recovery filter before physical packet injection:
\begin{itemize}
    \item \textbf{Accepted Tasks ($status = \text{"Assigned"}$):} The orchestrator spawns an asynchronous \texttt{\_route\_and\_execute\_task} process within the simulation environment, passing the planned forwarding path $\vec{P}_{up}(AP_r, i^*)$.
    \item \textbf{Transient Failures ($\text{"No\_Route"}$ or $\text{"Infeasible"}$):} A task marked with an infeasible status or lacking a physical ISL route at instant $t$ is not necessarily unservable; orbital motion may restore connectivity within seconds. The orchestrator re-enqueues the request into $\mathcal{B}$ while preserving its original arrival timestamp $t_{arr}$. If the re-enqueued requests saturate the buffer ($|\mathcal{B}| \ge BS$), $E_{ready}$ is triggered immediately.
    \item \textbf{Permanent Rejections ($\text{"Energy\_Exhaustion"}$, $\text{"Deadline\_Violation"}$, etc.):} Tasks dropped due to deterministic physical violations are logged directly at the entry gateway $AP_r$ via \texttt{record\_rejected\_task} and permanently discarded.
\end{itemize}

Algorithm~\ref{alg:task_dispatching} formalizes this dispatching and re-enqueuing engine, implemented in the \texttt{\_dispatch\_tasks} method of \texttt{Orchestrator.py}~\cite{bagini_repo_2026}.

\begin{algorithm}[H]
\caption{Task Dispatching, Re-Enqueuing, and Drop Accounting}
\label{alg:task_dispatching}
\small
\begin{algorithmic}[1]
\Require Assignment list $\mathcal{A}$, constellation nodes $\mathcal{N}$, task buffer $\mathcal{B}$, capacity $BS$
\Ensure Task process spawning, transient task re-enqueuing, and terminal drop logging
\ForAll{$task \in \mathcal{A}$}
    \State $t\_id \gets task.task\_id, \quad data \gets task.data, \quad status \gets task.status$
    \If{$status = \text{"Assigned"}$}
        \State Spawn discrete-event process: $\Call{RouteAndExecuteTask}{task, \mathcal{N}, env.now}$
    \ElsIf{$\text{"No\_Route"} \in status \lor \text{"Infeasible"} \in status$} \Comment{Transient orbital failure}
        \State Re-enqueue $(t\_id, data, AP_{global}, data.arrival\_time)$ into $\mathcal{B}$
        \If{$|\mathcal{B}| \ge BS$ \textbf{and} $\neg \Call{IsTriggered}{E_{ready}}$}
            \State $\Call{TriggerEvent}{E_{ready}}$ \Comment{Trigger early batch for retry}
        \EndIf
    \Else \Comment{Deterministic drop (e.g., Energy Exhaustion, Deadline Violation)}
        \State $ap \gets AP_{global}[0]$
        \State $ap.\Call{RecordRejectedTask}{t\_id, data.type, env.now, data.image\_size, status, data.d\_cpu}$
    \EndIf
\EndFor
\end{algorithmic}
\end{algorithm}

\subsection{Resilient Hybrid Packet Routing}
\label{subsec:hybrid_routing}

In dynamic LEO constellations, planned ISL trajectories are vulnerable to mid-flight disruption. 
Thermal expansion, high-speed orbital plane crossings, antenna micro-vibrations, and transient Doppler shifts can degrade or break an inter-satellite link while a packet is in transit. 
Relying entirely on a pre-computed path risks packet loss. 
To achieve operational resilience, the data forwarding layer implements a dynamic hybrid routing protocol:
\begin{itemize}
    \item \textbf{Nominal Planned Routing (Phase A):} Under nominal conditions, the data packet follows the shortest-path trajectory $\vec{P}_{up}(AP_r, i)$ computed during topology mapping. At each node, forwarding occurs if the next scheduled link remains operational ($B_{curr, next} > 0$).
    \item \textbf{Emergency Geographic Greedy Fallback (Phase B):} If an intermediate forwarding link is severed ($B_{curr, next} \le 0$), the current node autonomously transitions to emergency greedy recovery. 
    The forwarding satellite queries its active physical neighbors via \texttt{get\_neighbors()}, calculates their Euclidean distance to the destination satellite using orbital position vectors (\texttt{get\_pos\_proximity}), and forwards the payload to the closest eligible neighbor.
\end{itemize}

\paragraph{Loop Prevention and Dead-End Recovery.} 
To prevent packet cycling during greedy fallback, each task maintains a traversal set $\mathcal{V}_{visited}$ inside its header metadata (\texttt{Task.visited}). 
Nodes already traversed are excluded from fallback selection. 
If a node encounters a topological dead end where all active neighbors are either broken or already in $\mathcal{V}_{visited}$, the packet is dropped with status \texttt{"DROPPED\_GREEDY\_DEADEND"}, preventing buffer congestion.

Upon arrival at the destination node $i^*$, transmission latency and hop counts are committed to \texttt{globals.gbl\_generated\_tasks\_data}, and the thread yields to the compute queue simulator (\texttt{ILP\_simulation.TaskAssignment\_ILP}~\cite{bagini_repo_2026}). 
Algorithm~\ref{alg:hybrid_routing} details the complete hybrid routing and execution pipeline.

\begin{algorithm}[H]
\caption{Dynamic Hybrid Routing and Task Execution}
\label{alg:hybrid_routing}
\small
\begin{algorithmic}[1]
\Require Accepted task $r$, destination SEN $i^*$, pre-computed path $\vec{P}_{up} = (v_0, v_1, \dots, v_m)$ where $v_0 = AP_r, v_m = i^*$
\Ensure Reliable multi-hop forwarding and discrete-event CPU execution
\State Initialize $curr \gets v_0$, $idx \gets 0$, $is\_fallback \gets \mathbf{false}$, $\mathcal{V}_{visited} \gets \{v_0\}$
\While{$curr \neq i^*$}
    \If{$\neg is\_fallback$} \Comment{Phase A: Nominal Planned Path}
        \State $next \gets v_{idx+1}$
        \If{$B_{curr, next} > 0$}
            \State Forward payload across link $(curr, next)$
            \State $idx \gets idx + 1$, \quad $curr \gets next$, \quad $\mathcal{V}_{visited} \gets \mathcal{V}_{visited} \cup \{curr\}$
        \Else
            \State $is\_fallback \gets \mathbf{true}$ \Comment{Link broken: engage emergency recovery}
        \EndIf
    \EndIf
    \If{$is\_fallback$} \Comment{Phase B: Autonomous Geographic Greedy Forwarding}
        \State Retrieve neighbor set $\mathcal{N}_{active} \gets \{u \in \Call{Neighbors}{curr} \mid B_{curr, u} > 0 \land u \notin \mathcal{V}_{visited}\}$
        \If{$\mathcal{N}_{active} = \emptyset$}
            \State \Return \textbf{DROP}(\texttt{"DROPPED\_GREEDY\_DEADEND"})
        \EndIf
        \State Select best neighbor: $next^* \gets \arg\min_{u \in \mathcal{N}_{active}} \Call{EuclideanDistance}{\mathbf{p}_u, \mathbf{p}_{i^*}}$
        \State Forward payload across link $(curr, next^*)$
        \State $curr \gets next^*$, \quad $\mathcal{V}_{visited} \gets \mathcal{V}_{visited} \cup \{curr\}$
    \EndIf
\EndWhile
\State Record transfer latency $T_{transfer} \gets t_{now} - t_{arr}$ and final hop count $|\mathcal{V}_{visited}| - 1$
\State Yield to discrete-event simulator: $\Call{TaskAssignmentILP}{env, SelectedServer, TaskData}$
\end{algorithmic}
\end{algorithm}

\section{Computational Complexity and Scalability Analysis}
\label{sec:complexity_analysis}

Deploying mathematical optimization within dynamic LEO constellations introduces fundamental trade-offs between theoretical optimality and runtime overhead~\cite{icdcs_satellite_2025}. 
To establish the operational bounds of the centralized architecture, this section formalizes the asymptotic time and space complexity across the three pipeline stages: topology mapping, ILP solver resolution, and packet forwarding.

\subsection{Topology Mapping and Pathfinding Complexity}
\label{subsec:complexity_mapping}

Prior to solver instantiation, the orchestrator maps the constellation routing fabric using a Multi-Source Dijkstra shortest-path algorithm over the directed graph $G = (V, E)$~\cite{dijkstra1959note}. 
The node set $V = AP_{global} \cup S$ comprises all active regional access points and candidate satellites, while $E$ represents active ground-to-satellite links and inter-satellite links~\cite{icdcs_satellite_2025}.

Using an adjacency list representation paired with a binary min-heap priority queue (via Python's \texttt{heapq} module), the asymptotic time complexity across all active access points $|AP|$ is:
\begin{equation}
    \mathcal{T}_{map} = \mathcal{O}\left( |AP| \cdot \left( |E| + |V| \log |V| \right) \right)
    \label{eq:mapping_time_complexity}
\end{equation}
In standard Walker-Delta constellations, satellite transceivers are hardware-limited to at most four optical heads: two intra-plane links to ahead/behind peers and two inter-plane links to adjacent orbital planes~\cite{walker1984satellite, chen2021isl}. 
Consequently, the maximum node degree is strictly bounded ($\text{deg}(v) \le 4$), yielding a sparse graph where the total edge cardinality scales linearly with constellation size:
\begin{equation}
    |E| \le 4|S| + 2|AP| \implies |E| = \mathcal{O}(|S|)
\end{equation}
Substituting this structural property into Equation~\eqref{eq:mapping_time_complexity} yields an effective time complexity of:
\begin{equation}
    \mathcal{T}_{map} = \mathcal{O}\left( |AP| \cdot |S| \log |S| \right)
\end{equation}
Regarding auxiliary memory footprint, the orchestrator stores the adjacency graph, node telemetry vectors, and pre-computed paths. 
The space complexity is $\mathcal{O}(|AP| \cdot |S| + |E|)$. For regional constellations ($|S| \le 50$), this requires under a few megabytes, fitting comfortably within the memory constraints of embedded aerospace processing boards.

\subsection{ILP Formulation and Branch-and-Cut Solver Complexity}
\label{subsec:complexity_solver}

For an active batch containing $|R|$ buffered tasks and $|S|$ candidate Satellite Edge Nodes:
\begin{itemize}
    \item \textbf{Decision Variable Space:} The model allocates $|R| \cdot |S|$ binary assignment variables $x_{r,i}$ alongside $|R|$ binary drop variables $y_r$. The total decision dimension is:
    \begin{equation}
        \mathcal{D}_{vars} = |R| \cdot |S| + |R| = \mathcal{O}(|R| \cdot |S|)
    \end{equation}
    \item \textbf{Constraint Matrix Dimensions:} The constraint system enforces $|R|$ uniqueness equations, $|R| \cdot |S|$ deadline compliance bounds, $|S|$ fleet battery budget limits, and $|S|$ load balancing bounds. The total constraint row complexity is:
    \begin{equation}
        \mathcal{C}_{rows} = |R| \cdot (|S| + 1) + 2|S| = \mathcal{O}(|R| \cdot |S| + |R| + 2|S|)
    \end{equation}
\end{itemize}

While 0-1 Integer Linear Programs are strongly NP-hard in the general case, with a worst-case complexity of $\mathcal{O}(2^{|R| \cdot |S|})$~\cite{wolsey1998integer}, the modern branch-and-cut implementation in \texttt{HiGHS} mitigates combinatorial explosion through presolve reductions, cutting planes, and polynomial-time linear programming relaxations ($\mathcal{O}(n^{2.5})$) solved via the dual revised simplex method~\cite{huangfu2018highs, wolsey1998integer}.

The \emph{Dynamic Batching Engine} acts as an architectural boundary on problem scale. 
By capping batch size ($|R| \le BS$ with $BS \le 20$), the optimization problem space does not scale with external arrival rate spikes $\lambda$. 
For a representative regional constellation slice ($|S| \approx 15$), the model instantiates at most $300$ binary variables and $330$ constraint rows. 
Because the constraint matrix is sparse—each uniqueness constraint contains only $|S|$ non-zero entries, and each deadline constraint contains exactly one—the LP relaxations converge in fewer than $50$ simplex pivots, keeping solver execution time bounded within $T_{exec} \le 0.30\text{--}0.60\text{ ms}$.

\subsection{Hybrid Routing and Forwarding Complexity}
\label{subsec:complexity_routing}

The computational overhead of the forwarding layer depends on network link stability:
\begin{itemize}
    \item \textbf{Nominal Planned Forwarding (Phase A):} Forwarding nodes traverse the pre-computed Dijkstra path $\vec{P}_{up}(AP_r, i)$. Each hop requires an $\mathcal{O}(1)$ pointer lookup in the local routing table. The total time complexity for routing across $h_{up}$ hops is bounded by the network diameter:
    \begin{equation}
        \mathcal{T}_{planned} = \mathcal{O}(h_{up}) \le \mathcal{O}(\text{diam}(G)) \ll \mathcal{O}(|S|)
    \end{equation}
    \item \textbf{Greedy Recovery Fallback (Phase B):} If a planned link fails, the forwarding node evaluates adjacent neighbor distances. Sorting candidate neighbors requires $\mathcal{O}(k \log k)$ time, where $k$ is the physical node degree. Because optical transceiver architectures enforce $k \le 4$, this sorting step operates in negligible constant time:
    \begin{equation}
        \mathcal{T}_{greedy} = \mathcal{O}(k \log k) \approx \mathcal{O}(1) \quad (\text{since } k \le 4)
    \end{equation}
    Visited node lookups are evaluated against a hash-set structure ($\mathcal{V}_{visited}$), providing $\mathcal{O}(1)$ average-time checks and preventing forwarding loops.
\end{itemize}

\subsection{Constellation Scalability and Telemetry Overhead}
\label{subsec:complexity_scalability}

A central factor governing the feasibility of centralized orbital orchestration is the control signaling bandwidth required to maintain constellation state at the Master node~\cite{survey_orbital_edge_2023, icdcs_satellite_2025}. 
To construct the optimization model, the orchestrator periodically collects a compact telemetry vector $\mathbf{v}_i = [W_{cpu,i}, W_{net,i}, B_i, t_{sunset,i}]$ from each satellite.

Transmitting these telemetry updates across the ISL mesh introduces a control communication overhead of $\mathcal{O}(|S|)$ messages per update period. 
In regional deployments ($|S| \le 50$), telemetry updates consume less than $0.1\%$ of the available optical link bandwidth, ensuring that control signaling does not congest data transmission channels. 
However, as constellation scales grow globally to thousands of spacecraft ($|S| \gg 1000$), the propagation latency and stale-state overhead of a single master node become limiting factors, motivating regional partitioning or hierarchical decomposition for global deployments~\cite{icdcs_satellite_2025}.
